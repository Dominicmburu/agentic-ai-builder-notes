Week 4 · Lesson 20 · Project

Capstone: a multi-agent sales system

Bring the whole course together: a business-development manager agent with specialist sub-agents.

About 120 minutes to read Project Download the slides

The big idea

You will plan, build, test and present a system where a manager agent coordinates four specialists to help a sales team. This is the course in one project: prompts, tools, data, workflows, MCP, sub-agents and safety.

The system

AgentJobTools
BDM (manager)Understands the request, decides who helps, combines resultsThe four specialists as tools
ProspectingFinds companies that match the ideal customer profile and finds contactsFirecrawl (reads web pages) and Hunter.io (finds work emails), through MCP
SDR (sales development rep)Drafts a short, personal first messageDrafts only. Never sends
RevOps (revenue operations)Records results, checks data quality, reportsSheet or CRM
Account ExecutivePrepares a briefing before a meetingReads records, company notes
Everyday comparison: a small sales team The BDM is the team lead. Prospecting finds the leads, the SDR writes to them, RevOps keeps the books, and the Account Executive talks to the interested ones. You are building a digital version of that team.

Your starting files

  • Five workflow JSON files: starting versions of the manager and the specialists, to import into n8n.
  • ICP.pdf: the Ideal Customer Profile, a description of the kind of company we want to sell to.

Use the files your teacher shares. In n8n, import a file from the workflow menu. Then replace placeholder credentials with your own.

Step 1: plan before you build

Fill this in first. It takes thirty minutes and saves hours.

Planning questionMy answer

What is the one request the BDM should handle best?
Which agent does what? (one line each)
What can each agent not do?
Which actions need a person to approve?
Which trifecta ingredient am I removing?

Step 2: build in this order

  1. Import and run each specialist alone. Make sure each one works by itself with a fixed test input.
  2. Connect Prospecting to its MCP tools (Lesson 18). Allow only the tools it needs.
  3. Make the SDR draft, not send. Its output goes to a draft or a sheet for review.
  4. Make RevOps record results with consistent fields: company, contact, status, date.
  5. Add error handling (Lesson 17): retries for lookups, an error branch, and an error workflow.
  6. Assemble the BDM. Attach the specialists as tools with clear names and descriptions (Lesson 19) and write the manager prompt.
  7. Test the whole system using the table below, then fix and test again.
Safety rules for this project Draft, never send. Use test companies and your own email address for tests. Keep keys in credentials. A web page that Prospecting reads is untrusted content, so Prospecting must not be able to send anything out or see private records. That is how you break the trifecta.
Real people's data Contact details are personal data. In real work, check the rules on collecting and using them (consent, opt-out, data-protection law where you live) and keep only what you need. For this course, keep to company information and your own test contacts.

Step 4: the one-page write-up

Answer these in one page:

  1. What it does, in two sentences a customer would understand.
  2. How it works: a simple diagram and one line per agent.
  3. How well it works: your test score, and the failures you found.
  4. What could go wrong: the biggest risk and how you reduced it.
  5. What you would do next.

Step 5: the demo

Aim for 5 minutes:

  1. The problem (30 seconds): what the sales team struggles with.
  2. The live run (2 minutes): give the BDM one request and show the specialists being used. Open the execution so people see who did what.
  3. A failure on purpose (1 minute): show a request that should be refused or approved first, and what the system did.
  4. Your results (1 minute): the test score and one thing you fixed.
  5. Questions (30 seconds).
Prepare for live demos to go wrong Have a saved successful run ready to show. Test your internet and keys ten minutes before.

How it will be judged

AreaStrong work looks like
DesignEach agent has one clear job, a short prompt and only the tools it needs
Working systemThe manager delegates correctly on most test requests
SafetyThe trifecta is broken on purpose, nothing is sent unapproved, and no secrets are in files
ResilienceFailures are retried or recorded, not hidden

If something goes wrong

What you seeWhat it usually means
The manager picks the wrong specialistTool names and descriptions overlap or are vague. Make each one say exactly what it does and does not do.
A specialist works alone but fails inside the managerThe manager passes it the wrong input. Look at the execution to see what was sent.
Prospecting returns nothingThe MCP connection or key is wrong, or the tool is not allowed. Test the tool alone.
Runs are slow or costlyToo many specialist calls, or long prompts. Trim, and answer simple requests directly.
Imported workflows show red credential warningsPlaceholder credentials. Select your own in each node.

Quick quiz

Click an answer. You will see right away if it was correct, and why.

1. What does the BDM manager agent do?

It is the team lead. The specialists do the specific jobs.

2. Why must the SDR agent only create drafts?

A sent message cannot be unsent, and AI makes mistakes.

3. Why should Prospecting not be able to send data out or see private records?

Untrusted content plus private data plus a way out is the dangerous combination.

4. When should you write your test requests?

Tests written first stop you from only checking what you already know works.

5. Which tools does the Prospecting agent use in this project?

MCP connects the agent to outside services in a standard way.

Recap and what comes next

  1. The capstone is a manager agent (BDM) with four specialists: Prospecting, SDR, RevOps and Account Executive.
  2. Plan first, build each specialist alone, then assemble the manager. Draft, never send. Break the lethal trifecta on purpose.
  3. Write ten tests before fixing, record honest results, and show your work in a one-page write-up and a five-minute demo.

Next: You have finished the course. You can now explain how agents work, build them in code and in n8n, give them voice, data and tools, and judge when they are safe to use. Keep building small projects, and keep testing honestly.
