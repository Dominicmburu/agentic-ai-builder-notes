Advanced integrations

Send data with POST, split work into sub-workflows, and handle errors without panic.

About 50 minutes to read Integration Download the slides

The big idea

Real workflows must survive real life: services go down, replies come back wrong, and a workflow grows too big to read. This lesson gives you three habits: call APIs properly, split big workflows into small ones, and plan for failure.

By the end you can:

  • Pick the right authentication and send a POST request with JSON from n8n.
  • Split a large workflow into reusable sub-workflows.
  • Add retries and an error branch so failures are handled, not hidden.

Recap: choosing authentication

PatternWhen to use it
API keyThe service gives you a key. Simplest. Store it in an n8n credential.
Pre-configured OAuth2n8n has a built-in login for the service (Google Sheets, Gmail). Click and approve.
Custom OAuth2The service offers only OAuth2 and n8n has no ready login. You register an app yourself.

Always try the easiest that the service supports.

The HTTP Request node

If n8n has no ready-made node for a service, the HTTP Request node can call any web API. You already did this by hand in Lesson 1.

  1. Set the method (GET to fetch, POST to send).
  2. Paste the URL from the service's documentation.
  3. Choose authentication and pick a saved credential. Do not type keys into the node.
  4. For POST, switch on Send Body, choose JSON, and fill in the fields the documentation asks for.
An example JSON body
{
  "name": "{{ $json.name }}",
  "email": "{{ $json.email }}",
  "message": "{{ $json.summary }}"
}

The double curly braces are expressions from Lesson 9. They fill in the real values for each item.

Read the documentation of the service Every API has its own address, field names and rules. Copy them exactly from the service's current documentation. A single wrong field name gives an error.

Sub-workflows: small pieces you can reuse

A workflow with fifty boxes is hard to read and harder to fix. Move a repeated or self-contained job into its own workflow, then call it from the main one with the Execute Workflow node.

Everyday comparison: a recipe card A big cookbook says “make the sauce (page 12)” instead of repeating the sauce steps in every recipe. A sub-workflow is page 12.
  1. Create a new workflow and start it with the Execute Workflow Trigger node. Build the job after it.
  2. In the main workflow add Execute Workflow and choose the sub-workflow.
  3. Pass the data it needs as inputs, and read what it returns.

Benefits: one fix updates every place that uses it, you can test the piece on its own, and agents can use sub-workflows as tools (Lesson 19).

Planning for failure

Things go wrong: a service is down, a limit is reached, a field is missing. Three tools help.

1. Retry on fail

In a node's settings, switch on Retry On Fail, and set how many tries and how long to wait. Good for short outages.

2. Continue on error

Setting for a node: On Error, choose to continue using the error output. The workflow takes an error branch instead of stopping.

3. Error workflow

A separate workflow that starts whenever any workflow fails, and alerts you. Use the Error Trigger node.

Everyday comparison: a delivery If nobody answers the door, the courier tries again later (retry). If it still fails, they leave a note and carry on with other parcels (error branch). The depot manager gets a report of every failed delivery (error workflow).
Do not retry blindly Retrying is safe for reading data. It can be dangerous for actions like sending money or emails, because a retry may do the action twice. Think about what repeating the step would do.

Test your error handling on purpose

A free testing site, httpbin.org, will answer with whatever status code you ask for:

URLWhat it does
https://httpbin.org/status/500Always fails with a server error (500)
https://httpbin.org/status/429Says “too many requests” (429)
https://httpbin.org/status/200Succeeds (200)

Point an HTTP Request node at the 500 address, switch on retries and an error branch, and watch what happens. Then point it at the 200 address and check that the normal path still works.

Your exercise

Build a workflow that sends data to an API with POST, uses a sub-workflow for one step, and handles a failure by logging it and carrying on.

  1. HTTP Request node: POST a small JSON body to https://httpbin.org/post (a safe test address that echoes what you send).
  2. Move the step that formats the message into a sub-workflow, and call it.
  3. Add a second HTTP Request to https://httpbin.org/status/500 with retries on and an error branch.
  4. On the error branch, write a row to a sheet, or set a field such as failed: true, so the failure is recorded.

If something goes wrong

What you seeWhat it usually means
401 or 403The key is missing, wrong or lacks permission.
400 or 422The JSON body is wrong: a missing or misspelled field.
429You are sending too fast. Slow down or add a wait.
The sub-workflow returns nothingIts last node did not output data, or the wrong workflow was selected.
The error branch never firesThe node's On Error setting is still “stop workflow”.
The same email went out twiceA retry repeated an action. Do not retry actions that cannot be repeated.

Quick quiz

Click an answer. You will see right away if it was correct, and why.

1. Which node can call almost any web API?

When there is no ready-made node, HTTP Request does the job.

2. Why use a sub-workflow?

It is the recipe-card idea: write it once, refer to it.

3. Which setting makes a node try again after a failure?

Retries help with short outages.

4. What is risky about retrying a step that sends an email?

Retries are safe for reading and risky for actions that cannot be repeated.

5. What does the Error Trigger node start?

It is the depot manager who gets a report of every failure.

Glossary

HTTP Request node
An n8n node that calls any web API.
Request body
The data sent along with a POST request, usually JSON.
Status code
A number in the reply that says how it went: 200 worked, 4xx your mistake, 5xx their problem.
Sub-workflow
A workflow called by another workflow, like a reusable recipe card.
Execute Workflow
The n8n node that runs another workflow.
Retry On Fail
A node setting that tries the step again after an error.
Error branch
A path the workflow takes when a node fails, instead of stopping.
Error Trigger
The start node of a workflow that runs when another workflow fails.
Rate limit (429)
A service telling you that you are sending too many requests.

Recap and what comes next

  1. Use the easiest authentication the service offers, and keep keys in credentials. HTTP Request with a JSON body covers services without a ready-made node.
  2. Split big workflows into sub-workflows you can reuse and test separately.
  3. Plan for failure: retries for short outages, error branches to carry on, and an error workflow to alert you. Never blindly retry actions that cannot be repeated.
